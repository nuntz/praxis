# One tool seam, and every change reports its Effects

Everything Praxis can do inside a Context is a tool in one registry, and the screen, the Agent and an MCP caller all go through it. A write tool is one thing that can happen (finish a Task, delegate it, record an Entry), not a patch to a record. Every write returns the record it changed and a list of Effects: every record made, changed or deleted, the record itself among them, what happened to each, and whether the call did it directly or a rule did. A call that changes nothing says so. The same Effects go into a change log kept in the Context's object, each with the caller that made it. We decided this because a Task's state is derived from what has happened to it, so a tool that sets fields can express changes that are not events, and because an MCP caller sees nothing but the result of its call, so a result that leaves out what a rule did next leaves that caller wrong about the Journal.

## Considered Options

- **One patch tool per kind of record**, such as `update_task` with optional fields. Rejected: fewer tools for a model to hold, but the server has to work out from a diff what was meant, and a caller can ask for a combination that is not a thing that happens.
- **A smaller or coarser set made for MCP.** Rejected: a second surface is a second place for a rule to be missed, and an outside model deserves the same Effects the Agent gets.
- **Read endpoints shaped for screens**, sharing only the writes. Rejected: a capability the Agent cannot reach is not agentic-first, and screens needing good reads is the pressure that keeps the views good.
- **Returning only the changed record** and letting callers read again. Rejected: a caller does not know what to read again, and a model narrating a bare success says "done" whether or not anything happened.
- **A Context as an input to a tool.** Rejected: nothing crosses a Context, and a tool that cannot name another Context cannot reach one.
- **A general batch tool** running a list of calls in one transaction. Rejected: it multiplies every held and refused case. A compound change exists only as a named tool.
- **A bare `create_task`** that writes a carrying Entry from the Task's title. Rejected: every Task has an Origin Entry and its words should be what was said, not something the server made up.
- **Versioned tool names or a versioned endpoint.** Rejected: a Deployment is one person who upgrades everything at once, and an MCP client reads the tool list each time it connects.

## Consequences

- There are two registries. Context tools run inside one Context's object and take no Context as input: the Context is fixed by the Conversation, the Connection or the screen before the call arrives. Deployment tools (Contexts, moving a record, Connections, Devices, deleting a retired Context's data, export) run on the Deployment object and are offered to the person's hand only.
- The MCP surface is the Context tools under the same names and schemas, less those never offered to an MCP caller, with held calls refused. Praxis exposes tools only over MCP, no resources or prompts, and sets the read-only and destructive hints from the tool's own metadata. A Connection may be limited to reading; it scopes nothing else beyond its Context.
- The screen reads and writes only through tools. Tapping a Held Change and emptying the Trash are tools offered to the person's hand only. A connected PWA receives the Effects of each change and patches what it shows.
- A Task is made only with an Entry named: `record_entry` takes the words and a list of Tasks to make with it, and `add_task` attaches one to an Entry that exists. The editor parses an Inline Task into that list; the server never reads words to find Tasks.
- A link in `record_entry` or `add_link` may name a new Person or Project to make in the same call. The server does not guess that two Persons of one name are the same.
- Reads are a few named views, one filtered list per kind, get by id, one text search and `list_changes` since a cursor. Lists are paged by cursor with a default of 50. Every Task in any result carries its derived state and the reason for it, so no caller works out state. Effects use the same one-line summaries of a record that reads do.
- `list_changes` serves the PWA catching up, an MCP caller polling and the Agent, which is given a bounded digest of what changed since the last Message it answered. The log is kept 90 days (ADR 0010).
- The record a write is about is one of its Effects, made or changed by the call, so the Effects alone say everything the write changed and the change log, which holds only Effects, misses nothing.
- A write to a Context's settings, such as its time zone, changes no record, yet it is a change callers and the change log must see. It reports an Effect on the Context itself, carrying the Context's id and its name as the summary. A Context is still not a record.
- A Deployment tool that makes or changes a Connection reports an Effect on the Connection the same way, with its id and its name, and retiring a Context reports each Connection it ends as an Effect of that rule, as deleting one reports each Connection deleted with it. A Connection is not a record, and the Deployment object keeps no change log, so these Effects go to the caller only.
- A Held Change is not a record either. Leaving, making, cancelling and lapsing one each report an Effect on it, with its id and its summary, which holds none of the Entry's words. They go in the Context's change log, so the screen hears them, and `list_changes` gives a Connection none of them, since a Connection is never shown a Held Change: the person's tap shows to it only as the change it made to the Entry.
- A Device tool reports an Effect on the Device the same way, with its id and its name: made when something is first switched on there, changed when renamed or switched, and deleted when it leaves the list. A Device is not a record, and these Effects go to the caller only. When it was last seen is a sighting, not a change, and reports none.
- Moving a record between Contexts reports each record of the unit deleted in the Context it leaves and made in the one it goes to, and each record that stays and lost a link changed by rule, each Context's Effects in its own change log. `move_record` returns them all once the unit has arrived, and the source's alone, saying so, when the destination did not answer.
- Setting the spend cap reports an Effect on the cap the same way, with its fixed id and its new amount as the summary. The cap is not a record either, and the Effect goes to the caller only.
- Every write accepts an optional key from the caller, remembered for 30 days per caller; a repeat returns the first result and does nothing again. A key given again with another tool is invalid input, since its first result is the answer to a different call. The Agent's calls get a key from the runtime. The length is set by how long an Unsent write may wait on a Device (ADR 0020).
- Recording an Entry and finishing a Task accept the time they were made, offered to the person's hand only and refused if it is in the future. It sets the Entry's time and the Task's closing day; the call is otherwise judged against the Journal as it is on arrival, and the change log records when it arrived.
- A link in `record_entry` that names a record now in the Trash is recorded dormant, as if the record had been deleted afterwards. An Entry's words are never refused for a link.
- Only a change to an Entry's words says which version it was made against, and is refused as stale if the Entry has moved on. Any other call that asks for what is already so succeeds with no Effects.
- A result is a success or an error from a closed set of codes: not found, invalid input, not offered to this caller, held, stale, refused. A refusal lists as data each thing in the way, and a change is refused only for what it brings, not for faults already there. For the Agent a held call is not an error; it returns the Held Change it left.
- A call never states its Author; the tool layer stamps it from who is calling. Tool input carries a date as a date, never as prose; the caller resolves "next Friday" with the Context's time zone.
- The set may grow and inputs may gain optional fields freely. The spec lists each tool by name, purpose, who it is offered to and when it is held; the schemas live in the domain package.
- A write that changes only what is derived, `rebuild_search_index`, changes no record and nothing a caller reads but whether search uses meaning yet. It reports no Effect, puts nothing in the change log, and returns what it set going, the Entries still to embed, in place of a record (ADR 0023).
