# An object upgrades itself on waking, and a deploy is a one-way door

Each Durable Object upgrades its own tables when it wakes, before it serves anything, by running a ladder of numbered steps. The ladder goes forward only, there is one for a Context's object and one for the Deployment object, each object records the last step it finished, and a released step is never edited or dropped, so the ladder reaches back to the first release for good. Each step is its own transaction. An object whose step fails stays whole on the earlier step and serves nothing, reads included, until a fixed release is deployed; so does an object that finds its tables newer than the code. We decided this because an object that is awake is then always current, so no code path meets an old table; because the daily Backup already wakes every object, retired Contexts included, so no sweep is needed; and because the other way to allow going back, keeping every change readable by the previous release, makes every change take two releases for a rollback one person on their own Deployment will rarely want.

## Considered Options

- **A sweep at deploy that visits every object.** Rejected: one more step that can be skipped or half-finished, and the daily Backup already upgrades every object within a day.
- **All pending steps in one transaction.** Rejected: a failure at one step would undo the ones before it, and a Deployment left alone for a year would upgrade in one large transaction.
- **Serving reads from an object that failed to upgrade.** Rejected: it is new code reading old tables, which is guessing.
- **Every change readable by the previous release**, so the code can be rolled back. Rejected: each change becomes two releases, and it allows two versions to run side by side, which nothing here needs.
- **A floor on the ladder**, with older Deployments upgrading through an intermediate release. Rejected: it turns a neglected Deployment into an upgrade in stages done by hand. Steps are small and each stays under test.
- **Down steps.** Rejected: a second ladder that is never run until the day it matters.
- **One version number for the tables and the Export's format.** Rejected: the tables change often and the file should change rarely.

## Consequences

- There is no gradual rollout. Once any object has woken under a release, going back is by fixing forward, or by restoring a Backup into a fresh Deployment. A fix to a bad step is a new step.
- The deploy, which ADR 0026 makes the repository's CI run on a push to master, checks that a Backup from the last day exists and stops with a warning if not, which the person can override with a line in the pushed commit's message. Skipping releases needs no ceremony. A release is the commit deployed.
- Before its first pending step an object notes the platform's point-in-time bookmark. Returning one object to that moment is an operator's escape hatch described in the docs, not a feature. A new object holds nothing to return to, and notes none.
- A step changes shape, never meaning. It writes nothing to the change log, has no Author, makes no Version and never touches an Entry's words. Every read through a tool returns the same before and after, apart from what the release adds. A change in meaning to existing records is a rule of the release that the spec states.
- A step carries across what the Export does not hold: the change log, Devices and their push subscriptions, and a Connection's standing. An upgrade never ends a Connection, silences a Device or shortens the change log.
- A step never migrates anything outside the object. When a release changes what the meaning index holds, the step marks the index as stale and it is rebuilt from the Journal.
- The runtime's tables are not on Praxis's ladder. A runtime that cannot open its tables never blocks the Journal: the screen and Connections keep working, the Conversation shows as unavailable, and starting it afresh is the person's choice.
- A Context whose object is stuck is named in a standing Notice, and the other Contexts keep working. Everything on its clock stops: no Brief or Review, no Trash expiry, no finishing of an interrupted move, and a move into it is refused. It tries again only when woken under a different release. When it comes back, anything in its Trash past 30 days from its delete is removed.
- The daily Backup carries on for the other Contexts. The last Backup that holds a stuck Context is kept past 30 days until that Context upgrades, and the Notice says so. For that long, a record removed for good from that Context may still be in a file Praxis holds.
- If the Deployment object is stuck, nothing can be routed. The Worker shows one plain page saying the upgrade failed and under which release. That object holds no Journal, so its steps are few and small.
- The Export's format version has its own ladder, which brings an old file forward as it is read and reaches back to format 1 for good, since a downloaded Export has no age limit. A file newer than the code is refused.
- Each release that adds a step commits one fixture: a Context object and a Deployment object filled by a fixed scenario run through the tools at that release, saved as a dump beside the Export it produced. A fixture is named by the tops of its two ladders, so a release that adds no step, whose tables are the one before's, needs none of its own. The upgrade test wakes every fixture under the current code and checks that its tables have the same shape as a freshly made object's, that its Export equals the saved Export brought forward through the file's ladder, that a few reads through the tools still show the change log, the Devices and a working Connection, and that a step made to fail leaves the object whole on the earlier step and refusing calls. A guard fails CI when a released step's text changes.
