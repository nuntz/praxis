# Pi Durable in Praxis

How the Agent's runtime (ADR 0024) is wired into a Context's object, and what it does that its README does not make plain. Read this before changing `apps/worker/src/agent.ts` or `apps/worker/test/model-fake.ts`.

Pinned at `@earendil-works/pi-durable`, `pi-ai` and `chord` **1.7.0**, which move together. The API is marked experimental and changes between releases: check the installed types, under `node_modules/.bun/@earendil-works+pi-durable@*/node_modules/@earendil-works/pi-durable/dist`, before trusting this page or the README.

## The shape

- **A plain Durable Object, no wrapper.** `ContextAgent` (`agent.ts`) opens the Harness itself with `openDurableObjectSqliteStorage(ctx.storage, { prefix: "pi_" })`, lazily on the first Conversation tool or alarm, since most requests never need it. Cloudflare's `agents` package and its `PiHarness` are not used.
- **One alarm for both.** The runtime gets `onWake`, and the Context's object folds what it says into the alarm it keeps for its own work (`keepAlarm` in `context-object.ts`): a heartbeat while the runtime is `active`, its `at` when it sleeps, the daily pruning, and the next Brief or Review or a try at one. The object keeps its own clock, the real one moved by where the last request or wake set it (`#clockSkew`, none when deployed), and the platform's alarm is armed by the real clock it stands from, so a test's object never wakes by itself at the real time. The alarm calls `resume()`. Arm before anything that can start work (`send`), since a missing alarm strands a Run.
- **Praxis's own writes beside the runtime's.** The runtime commits through `ctx.storage.transaction` with async callbacks that await only in-object SQL, so Praxis's `transactionSync` writes never land inside one. Keep it that way: nothing in a runtime commit may await a model, a fetch or another object.
- **One Conversation:** the runtime's root. A person's Message is placed with `entry: { kind: "praxis.message", data }` and the data is what the screen shows. The model is shown `content`, which carries the Run's bearings before the words.
- **A Run's record and the runtime:** `startRun` keeps the record before the Run starts, keyed by the runtime's submission id. `#settle` waits on the submission and closes the record. On open, every record not ended is waited on again, so a restart cannot leave one open.
- **Tools:** every Context tool in the Agent's column, `replay: "safe"`, each write given the key `run:<callId>`, so a call run again after a crash returns its first result. The schema the model sees drops `key`. A tool's `execute` runs outside the runtime's commits, so it may wait: the host's `call` answers once the tool has, and the tools the Context's object runs itself, `search` among them, go through the same path as any caller's call to them, waiting on the meaning index and the Deployment object (#106).
- **Each turn's bearings ride in the Message's `content`**, not in a prompt section, so the preamble stays the same and the model's prompt cache holds. A Run answering a new Message keeps `told_through`, where the change log stood when the Agent was told what changed, and the next Message's digest starts there.
- **The round limit is the runtime's `maxTurns`**, set on the root agent with the model and configured again on open when it differs. A Run that reaches it settles `unanswered` with reason `turn_limit`, which Praxis records as `cut_short`, not as a failure; its Message gets Praxis's sentence saying so when the page is read, since the model was not asked again, and the next Message's bearings tell the Agent so (never a Brief's or Review's).
- **`maxTurns` is the Conversation's, not a Run's**, so a `beforeRequest` hook on `GenerationTask` configures it for the Run it is about to ask the model for: 10 for a Brief or Review, 25 for a Run answering the person. The runtime reads it once a round's tools have run, from the agent resolved for that phase, so a configure committed before the round counts for it; one committed during the phase that reads it would not. The same hook takes every tool but the clock's reads off the request's system messages for a Brief or Review, from both `toolsAdded` and `toolsRemoved`, and drops a system message left changing nothing. Its calls go to the registry as the `clock` caller, which refuses a write whatever the model was shown.
- **A changed tool declaration is removed and added again**: a Conversation woken under a release that changed one writes a system message with `toolsRemoved` and `toolsAdded`, and with every tool in both when the changed one would move (`planTools` in pi-durable's `harness/prompt.js`). Anthropic refuses a request that removes a tool it was never offered (`tool_reference_unresolved`), so a Brief that kept the removals of tools it is not offered failed on every try in the Context that held one.
- **A Brief or a Review is an `input` submission** whose record is of the kind `praxis.clock`, with data saying which and when, in place of a person's Message, so it queues behind a Run going like one and a Message queues behind it. Its answer is not carried down the live channel as it is written: it arrives whole once it has ended with something to raise, and a page leaves out one going, one with nothing to raise and one a newer of its kind replaced unread.
- **Praxis writes the compaction summary** in a `beforeCompact` hook on `CompactionTask`: it asks the model on its own prompt (`compaction.ts`), over the Messages with their bearings taken out, adds the waiting Held Changes itself, and counts the call's tokens on the Run answering (`addRunSpend`). `backgroundTokens: 0` keeps every compaction blocking, inside a Run, so the cost has a Run to count in.

## Gotchas

- **`agent()` in the Context's object opens the Agent and fixes its model** for as long as the object lives, so a test's script must come first (`scriptModel` in `test/model-fake.ts`): a test that needs the model to change, say from unreachable to answering, scripts once and switches inside the script, as `heldAnswer()` does. The harness fails a test in which a Context asked a script the test had since replaced. Code that only needs to know whether there is an Agent, such as `keepAlarm`, asks `hasAgent()`, which opens nothing: calling `agent()` from `make` once broke every test that scripts after making its Context.

- **A Run's identity is `live.run.inputs[0]`**, the submission it answers. `live.run.taskId` is the generation task, which is handed on every model round, so it changes mid-Run.
- **The runtime calls its transcript records entries.** They are never Entries: Praxis code names them records, kinds or Messages (see Domain words in `CODING_STANDARDS.md`).
- **A scripted model's request carries the tools in its system messages**, not in `context.tools`: `normalizeContext()` moves them there, as `toolsAdded`, beside the prompt's sections under `sections`. `offeredIn()` in `test/model-fake.ts` reads both. A fake that branches on what it is offered reads the person's words instead (`lastWords`).
- **A person's Message in the model's context carries the bearings** before the words. Anything that reads one back, such as the compaction summary or a scripted model, takes the words with `personsWords`, since the bearings are given afresh each Message.
- **The faux provider streams in chunks of random size** unless `tokenSize` is fixed. `scriptModel(..., { wordsPerSecond })` fixes it at one token, so a test of the answer as it is written sees several partials every run.
- **Partials are deferred commits**, at most every 100 ms. `observeDoc(LiveDoc, …)` sees them at once; storage gets them later. Derive nothing durable from a partial.
- **A model the runtime refuses to call ends the Run `unanswered`** with a `runFailure` reason, and the submission's `reason` and `detail` (the provider's error text for `model_error`) say why. `runFailure()` in `model.ts` reads them as the key refused, the request refused or the model not reached (SPEC 5.6). The `detail` comes in several shapes, and only the provider's status and error type tell them apart, since its message can quote the request: `<status> <body>`, as the Anthropic SDK words an error, or `<status> status code (no body)` for one with no body; the body alone, for an error sent during a stream; the runtime's own words in front of either, such as `Compaction failed: Summarization failed: 400 {…}` from a blocking compaction that failed (`compactionFailure` in pi-durable's `harness/generation.js`); and, when the model itself declines (stop reason `refusal`), its explanation, or pi-ai's own sentence for one, with no status or body at all (#151). `runFailure` reads a status with no body only where it leads the text, and an answer with neither status nor type by the old words for a refused key. Praxis's `afterFailedRun: "continue"` answers the Messages queued behind it in their turn: `withdraw` would settle them without ever placing them, and their words would leave the Conversation.
- **The runtime retries, not the provider's client.** `settings.retry` takes the model's `retry` (seconds for the real one, a millisecond for the scripted one), and `stream.maxRetries: 0` stops the SDK asking again inside each attempt. A refused key or request is retried only when pi-ai's `isRetryableAssistantError` sees a transient error in it, and it matches words anywhere in the error text, so a refused request whose message quotes "server error" or "overloaded" is asked again a few times before it fails. Each failed attempt is kept in the transcript as an assistant record with `stopReason: "error"`, which the provider adapters skip when the model is next asked.
- **A hook that throws is reported and skipped**, as `extension_error`: for `beforeCompact` that means the runtime's own summarizer runs instead, on its own prompt. Praxis's hook never throws: when the model cannot write the summary it returns `{ kind: "decline" }`, and nothing is compacted that time.
- **The runtime's own summary is uncounted.** Its tokens go to `pi.usage`, not to any record, so the Run's spend would miss them: one more reason the hook declines rather than falls back.
- **Clearing the Conversation drops every table under `pi_`** (`dropRuntimeTables`), and the Context's object lets go of its `ContextAgent`, so the next use opens a runtime afresh, which makes them again, empty. The runtime numbers its records and submissions from 1 again, so each Run record's handles on the old Conversation (`submission`, `from_record`) are let go in the same transaction: kept, a new submission would name an old Run. So is `told_through`: the new Conversation was never told what changed, and its first Message is told the newest changes, as one never told. It is refused while any Run has not ended, since the runtime is working in the record it would drop. What came after its `up_to` is read first (`keptAfter`) and placed again after the drop as `write` submissions, each record as it was (`placeKept`), so no Run answers it again: a write of `kind`, `data` and `model` is accepted for the runtime's own `pi.assistant` records too, since only an input's kind is checked. The tools' system messages and a compaction's summary are not placed again; the runtime tells the model of its tools afresh. The Runs answering what was kept get `told_through` back, and `from_record` as its record now numbers (`keepHandles`).
- **Trying a failed Run again is a `continue` submission**, which answers the transcript as it stands, so it can only answer the newest Message. It places no record of its own, so its Run record keeps `from_record`, the first runtime record that may be its own, and its spend is counted from there.

## Upgrading from 1.5.2 to 1.6.0

[Pi Durable 1.6.0](https://github.com/earendil-works/pi/blob/v1.6.0/packages/durable/CHANGELOG.md)
changes `pi.tool` from version 3 to 4 and `pi.generation` from version 2 to 3. Its migrations
keep these older checkpoints. Praxis does not use the renamed `RunEndTask`, code-mode namespaces,
parked tools or signal-only sleeps, and does not read tool `durationMs`. No host API change is
needed. Pi AI's provider schema fixes travel with this upgrade; the tool seam checks that the
model sees the schema without the write key, that a missing required argument makes no write, and that
a valid call still works. These tests use the scripted provider, not a live provider request.

`test/fixtures/pi-1.5.2-pending/pending.json` was captured on master
`ec80ef02cf818d5e206885e319afea05b3a75bc1` with all three packages still at 1.5.2, using the fixture
Worker test configuration and `dumpObject` on native workerd Durable Object SQLite. A scripted
model called `record_entry`, then its second response was held with `heldAnswer`. The dump was
taken before releasing that response: submission 8 is still `placed`, generation 14 is running
in phase `request` at version 2, and tool 12 is already terminal at version 3. The fixture is
synthetic and contains no user data. It is separate from the ladder fixtures because no Praxis
ladder step changed.

`upgrade.test.ts` restores both objects, opens the Conversation under 1.6.0, checks that the
completed tool result reaches the next model request, and makes a second write. The original Run
ends answered, each Entry and change appears once, the pending generation becomes terminal at
version 3, a new tool runs at version 4, and another object restart preserves the results. This
covers a pending generation following a completed tool; it does not establish migration of a
tool interrupted during execution, a pending compaction, or the new signal/park paths.

Do not roll the Worker back to 1.5.2 after opening these objects under 1.6.0. The older Harness
can block newer tasks with `task_too_old` and treats a sleep without `until` as due. The runtime's
tables remain outside Praxis's ladder, so the ladder's newer-step guard cannot establish runtime
rollback safety. Follow ADR 0019: fix forward or restore a Backup into a fresh Deployment.
